# 衣装の定義 — 「何がその衣装をその衣装たらしめるか」

生成器のパラメータを決める前に、**対象を定義する**。ここが甘いと
「メッシュとしては健全で spec とも整合しているが、その衣装には見えない」ものが出る。

各項目には「生成側でどう作るか」と「検証側でどう測るか」を必ず対応させる。
検証できない定義は、次に壊したときに気づけないので定義した意味がない。

---

## プリーツスカート (knife pleat skirt)

### 参照した実物

| 出どころ | 内容 | 分かること |
|---|---|---|
| Auckland War Memorial Museum 収蔵の学校用プリーツスカート(1988-89, CC BY 4.0) | 平置きの実物写真。**ウエスト周 660mm / 丈 415mm** の実測値付き | 折り目線がウエストバンドから裾まで連続。裾で折り込みが扇状に開く。実寸の比率 |
| 着用状態のタータンプリーツスカート(CC BY-SA 2.0) | 正面〜斜めから着用した状態 | 腰では折り目が閉じて柄がほぼ歪まず、裾に向かって開く。シルエットはほぼ直線のAライン |
| 縫製の定石(複数の縫製解説) | 完全プリーツは**ウエスト周の3倍**の布。1プリーツ = 見え幅 w + 折り込み 2w = 3w。典型的な見え幅 1インチ(約2.5cm)。ウエストバンドから**3.5インチ(約9cm)下まで縫い止め**、その下で開放 | 山数と縫い止め位置の目安 |

実寸から出る比率(身長 1.6m の着用者を仮定):
- 丈 415mm → **丈/身長 ≈ 0.26**
- ウエスト周 660mm → **/身長 ≈ 0.41**
- 山数 = ウエスト周 660mm ÷ 見え幅 25mm ≈ **26山**
- 縫い止め 90mm ÷ 丈 415mm ≈ **丈の 0.22**

### 定義(この5つが揃って初めてプリーツスカートになる)

| # | 定義 | 生成側 | 検証側 |
|---|---|---|---|
| 1 | **折り目線がウエストバンドから裾まで連続する。** 上部は縫い止め/プレスで閉じているが、線は見えている | `pleat_taper` を上端の直下から非ゼロ(`pleat_closed`)にする | 上から2本目のリングの周期成分の振幅 ÷ 裾の振幅 ≥ 0.15 |
| 2 | **折り目の開きは下へ増える。** 腰では閉じ、裾で最大に開く | `pleat_closed` → 1.0 へ、縫い止め区間の下から滑らかに | 裾の振幅 > 上部の振幅 |
| 3 | **山数が一定で、周方向に等間隔** | 矩形波(`pleat_offsets`)。分割数は山数の2倍以上かつ倍数 | 半径列の周期成分が指定した山数の周波数に立つ(楕円ぶんは差し引く) |
| 4 | **裾がジグザグになり、布が周長より長い** | 折り込みの分だけ実周長が伸びる | 裾の実周長 / 設計周長 > 1 + depth/2 |
| 5 | **シルエットはほぼ直線のAライン**(朝顔状に反らない) | `flare_curve` ≈ 1.0 前後 | シルエットの幅プロファイルに当てはめた curve が 1.0 付近 |

### 踏んだ間違い

**最初の実装は #1 と #2 を取り違えていた。** `pleat_start=0.15` + smoothstep にしたため、
折り目が t≈0.4 まで開かず、**上半分が折り目のない滑らかな筒**になっていた。
「腰では畳まれている」を「腰では折り目が無い」と実装してしまったのが原因。
実物は腰でも折り目線は見えている(閉じているだけ)。

**メッシュは封筒(envelope)であって布ではない。** 「布量3倍」はウエストバンドに
縫い込まれた布の量で、封筒の表面には現れない。なのでこのメッシュで 3倍則は検証できない。
検証できるのは #1〜#5 のように**封筒の形として現れる性質**だけ。3倍則は山数を決める
根拠として使い、検証項目には入れない。

## フレアスカート (flared / A-line skirt)

プリーツスカートとの違いは**折り目が無いこと**。代わりに布の自重による
なだらかなドレープ(`drape_folds` / 余弦)が入る。折り目が立たないので、
分割数を増やすと波が消えていく(プリーツは何分割でも段差が残る)。

| # | 定義 | 検証側 |
|---|---|---|
| 1 | 折り目(矩形波)が無い | 宣言していない周期成分が出ていないこと |
| 2 | なだらかな波がある(入れた場合) | 指定した山数の周波数に振幅が立つ |
| 3 | 腰から尻に沿い、そこから裾へ広がる | 上端周長 = サイズ表のウエスト、裾周長 = ヒップ×flare |

## パンツ (pants / slacks)

腰からは1本の筒、股からは2本の脚。**分岐がある**のが他の全パーツとの違いで、
K1(リング列のロフト)だけでは作れない唯一の衣装。

### 参照した寸法

marea カタログのサイズ表 PDF(garments.md 上部で参照済み)にはパンツの行もあるが、
まだ転記していない。以下は**すべて設計値** — 出どころのある寸法(ヒップ等)から
製図の定石で導き、式を明記する。転記したらここを実寸で置き換えること。

| 項目 | /H | 実寸(158) | 導出(すべて設計値) |
|---|---|---|---|
| 股上 rise | 0.16 | 25.3cm | 製図の定石 股上 ≒ ヒップ/4 + 2.5cm(91/4+2.5) |
| 股下 inseam | 0.43 | 68cm | フルレングス総丈 ≒ 0.59H からの逆算(総丈 − 股上) |
| わたり(太もも周)thigh | 0.34 | 53.7cm | 製図の目安 ヒップ × 0.59 |
| 膝周 knee | 0.235 | 37cm | ヒップ × 0.41 |
| 裾周 hem_opening | 0.253 | 40cm | スラックスの標準裾幅 20cm(flat)× 2 |

### 定義(この4つが揃って初めてパンツになる)

| # | 定義 | 生成側 | 検証側(**先に決める**) |
|---|---|---|---|
| 1 | **腰から股までは1本の筒** | 腰〜股を skirt_profile(ウエスト→ヒップ)で閉じたロフトに | 上端リングの実周長 = ウエスト(ゆとり込み)±3%。股リングの深さ = 股上 ±5%(`pants_rise`) |
| 2 | **股から2本の脚に分かれている** | 股リングを前後中心で割り、股の縫い目(ブリッジ)を渡して脚2本の分岐リングを組む | 境界ループ = 3(腰1 + 裾2)。裾リングが2本あり、重心の x が左右対称(`pants_legs_symmetric`) |
| 3 | **脚は太ももから裾へ細くなる筒** | わたり→膝→裾の周長プロファイル(膝は t=0.5 に固定 — 解剖の位置。SLEEVE_ELBOW_T と同じ理屈) | thigh リングの実周長 = わたり×(1+ゆとり)±5%。裾の実周長 = 裾周 ±5%。裾の z = 股 − 股下 ±3%(`pants_inseam`) |
| 4 | **股が塞がっている**(スカートとの違い) | ブリッジの頂点を両脚で**共有**して溶接 | nonmanifold = 0(縫い目の辺が必ず2面に使われる)+ 境界ループ数が3ちょうど |

### K2(股の分岐)の作り

**K1 は「同じ頂点数のリング列」しか受けないので、分岐は表現できない。**
K2 = `kernels.weld_meshes`: 複数の K1 ロフトを、**一致する座標の頂点を共有させて**
1枚の PartMesh に溶接する。パンツ = 3本のロフトの溶接:

1. **胴**: 腰→股の閉じた筒(K1 のまま)
2. **脚×2**: 分岐リング = 股リングの半周 + 股の縫い目(前中心→後ろ中心を x=0 で渡る
   ブリッジ点列)。これを最上リングとして裾まで K1 でロフトし、袖と同じ
   smoothstep ブレンドで円形に馴染ませる
3. 溶接で: 股リングの外周辺 = 胴の面(上)+ 脚の面(下)の2面、ブリッジの辺 =
   左脚の面 + 右脚の面の2面(両脚が逆向きに辿る)→ 多様体と巻き方向が定義から成立

**制約と罠**:

- **segments は4の倍数必須。** 前中心・後ろ中心・両脇に頂点がないと股が割れない。
  spec の検証(`_modulation_errors`)で弾く(黙って丸めない — AI へのエラーが修正指示になる)
- 溶接後は「リング番号×分割数」の添字計算が使えない(hood_metrics 方式は不可)。
  検証に使うリングは builder が **mesh.rings に明示的に登録する**
  (`top` / `crotch` / `thigh_l` / `thigh_r` / `hem_l` / `hem_r`)
- `edge_kinds()` は quad の頂点順で分類するので溶接後も正しい(添字計算ではない)
- UV は3島(胴 + 脚2)。weld_meshes が横並びに 1/N ずつ詰める。島ごとに
  正規化されるためテクセル密度は島間で揃わない(既知の制限)
- 自己交差の第一容疑者は**股の直下**(両脚の内側の壁)。ブレンド区間(blend)を
  詰めすぎると貫通する

## ワンピース (one-piece dress)

胴(bodice)とスカート(skirt_body)をウエストで**縫い合わせた**衣装。
新しい builder は無い — 既存パーツの組み合わせ + bodice の `hem_style` 拡張だけで成立する。

### 定義

| # | 定義 | 生成側 | 検証側 |
|---|---|---|---|
| 1 | **胴の裾が水平**(シャツテールだとスカートが縫えない) | `hem_style: "flat"` で tails を 0 に | flat では design からシャツテールのキーが消え、裾ゲートは発火しない(shirttail の胴は従来どおり常時判定) |
| 2 | **ウエストで縫い合わさっている** | 胴の裾周長 = バスト×hem_scale をウエスト寸法に合わせる(0.405/0.525 = 0.7714。ease は分子分母で相殺)。skirt の waist_z を胴の裾 z(実測 0.622H @ length_scale 0.55)に合わせる | `kind: "sewn"` joint の seam_distance が許容差内 |
| 3 | 胴・袖・襟・前立て・ボタン・スカートの各定義 | 既存パーツのまま | 既存ゲートがそのまま効く |

### 実装メモ

- `hem_style` は _BODICE の enum(shirttail / flat)。**flat が design から
  `shirttail_drop` キーを落とす**ことでゲートを切り替える(値 0 での分岐は
  「設計 0 = 実測 0」で通ってしまうため、キーの有無をスイッチにする)
- ブラウスの既定は shirttail のまま(回帰ゲート全緑を確認してから preset を足した)
- sewn の seam_distance は一方向(a→b)。a = 胴の裾(前開きの楔で欠けている側)、
  b = スカート上端(全周ある側)にする

### 踏んだ間違い(定義 #19 の由来)

**ボタンが服から離れて浮いた。** ボタンは「前立て**全体の最前点** − standoff」の
一定 y に置かれていた。ブラウスは前面がほぼ垂直なので気づかなかったが、
ワンピースは胸の張り出し→ウエストへ前面が大きく後退するため、胸以外のボタンが
宙に浮いた。数値ゲート(#14 の「前立ての内側」)は x と z しか見ておらず、
y(前後)の浮きは**レンダーの目視でしか見つからなかった** — 原因3の再演。

対策(欠陥→ゲート→修正の順):

| # | 定義 | 生成側 | 検証側 |
|---|---|---|---|
| 19 | **ボタンは前立ての表面に沿う** | 前立てが表面プロファイル `placket_front_profile`(z, y)を出し、ボタンごとに**その高さの表面**から standoff だけ浮かせる。円盤は平らなままなので、傾く区間ではディスクの z 幅全体で最前値を取る(中心だけ見ると縁が布に食い込む) | シェル頂点ごとの「表面 y − 頂点 y」の**ボタン別最小値**が 0〜ボタン厚みの範囲(`buttons_touch_the_placket`)。中心1点の離隔で見ないのは、傾いた表面では平らな円盤の中心が正当に離れるため |

副作用も2つ踏んだ: (1) 厚みを部品全体の y 幅で測っていたため、表面に沿って前後の
段差が付いただけで「厚い円盤」ゲートに落ちた → シェルごとの y 幅に修正。
(2) 中心の高さだけで浮かせると傾いた表面で円盤の縁が布に食い込み交差ゲートに落ちた
→ ディスク幅の最前値から浮かせる。

## スクール水着 (swimsuit)

紺のワンピース水着 + 胸の白いゼッケン。**新しいカーネルもジオメトリ計算も足していない** —
ワンピースと同じく既存パーツの組み合わせで、追加したのは bodice の「前を閉じる」拡張と
ゼッケン(patch)の1パーツだけ。

構成: `bodice`(前閉じ・袖なし・裾は水平)+ `pants`(股下を極端に短くした脚口)
+ `patch` ×2(白いゼッケン + 紺の名入れバー)+ `apron`(旧スクの前スカート)。

### 定義

| # | 定義 | 生成側 | 検証側 |
|---|---|---|---|
| 1 | **かぶりもの**(前が開いていない) | `front_style: "closed"` で前中心に頂点を置いた全周の角度列 + `loft_rings(closed=True)` | 境界ループが**4本**(襟ぐり・裾・袖ぐり2)。前開きの3本と区別が付く |
| 2 | **袖ぐりは腕が通るだけ。開けすぎない** | `armhole_segments` 3(45°)・`armhole_depth_scale` 0.80(16.7cm)。さらに `shoulder_width_scale` 0.90 で**肩線を肩先まで伸ばさない** | `armhole_depth` も `shoulder_width` も**設計値が一緒に動く**ので逃げない。`shoulder_exists` が肩の渡りの下限を守る |
| 3 | **襟ぐりが広い**(スクープネック) | `neck_ease` を上げる。肩紐の幅 = 肩幅/2 − 襟ぐりの長半径 で決まる(1.0 で 6.2cm) | `neck_opening` が襟ぐり周長を、`shoulder_exists` が肩紐の幅を見る |
| 4 | **ウエストで縫い合わさっている** | ワンピースと同じ。胴の裾周長 = バスト × 0.7714 = ウエスト。pants の `waist_z` を胴の裾 z(0.60918H @ length_scale 0.55)に合わせる | `kind: "sewn"` joint の seam_distance |
| 5 | **股が閉じていて脚口が2つある** | pants をそのまま使う(K2 の分岐)。`inseam_scale` 0.03 = 股下 2.0cm の「脚口の帯」 | 既存のパンツゲート(rise / inseam / thigh / 左右対称)がそのまま効く |
| 6 | **胸に白いゼッケンがある** | `patch`。相手の前面プロファイルと**断面の長半径**をもらって楕円に沿わせる。白い矩形の上に紺の名入れバー(`patch` もう1枚)を重ねる | 幅・丈・前中心にあること・**胴より前に出ていること**(`patch_sits_on_the_front`) |
| 7 | **腰から前スカートが垂れている**(旧スクの署名) | `apron`。前中心を中心とした弧の範囲だけに、下の水着と同じプロファイル + standoff で張る | 上端の弧長が製図値(楕円弧)と一致・広がり・前中心・**前を向いていること**(`apron_faces_front`。後ろに回っていたらケープ) |

### 参照した寸法

人体寸法は既存のサイズ表のまま(新しい項目は足していない)。水着固有の値はすべて**設計値**:

| 項目 | 値 | 理由 |
|---|---|---|
| ゼッケン 幅×丈 | 0.105 × 0.070 /H = 16.6 × 11.1cm | 公表寸法が見つからない。学校指定品の名札の見た目から置いた**設計値**(実際の丈は行に吸着して 9.9cm) |
| 脚口の股下 | `inseam_scale` 0.03 = 2.0cm | 同上。股から数cmで終わる帯。`inseam_scale` の下限を 0.1 → 0.03 に下げて表現できるようにした |
| 生地 | roughness 0.55 / sheen 0.12 | 水着のニットは綿(0.78)より滑らか。**設計値** |
| 前スカート 丈×角度幅 | 0.095 /H = 15cm × 170° | 公表寸法が見つからない。旧スクの見た目から置いた**設計値**。`flare` は 1.0(体に沿わせる) — 1.12 にすると硬いペプラムのように反り返って前垂れに見えない |

### 実装メモ

- **`front_style` は front_gap を無効にするのではなく、design から `front_gap_width`
  キーを落とす。** 0 を入れると前立てゲートが「幅 >= 0」で素通りする
  (`neck_drop_scale` / `shirttail_drop` と同じ罠。キーの有無をスイッチにする)
- **ゼッケンは前中心に頂点が要る(columns は奇数に丸める)。** 偶数だといちばん前へ
  出る頂点が中心からずれた列になり、そこは断面が後ろへ逃げているぶん浮きが目減りして、
  設計どおり作っても「胴の前面より手前」の検査に落ちる
- **ゼッケンの縦の刻みは相手の行に吸着させる。** 前立てのように折れ点を混ぜつつ
  等間隔の点も足すと刻みが不揃いになり、軸方向エッジ長のばらつきの検査に落ちる。
  行に乗せると食い込み防止と刻みの均一性が同時に立つ。**代わりに丈は指定どおりに
  ならない**ので、design の丈は吸着後の実寸にする
- 幅のある布を前面に貼るには前中心の y だけでは足りない。胴が前面の**実物**
  (`front_surface`: 行ごとの (x, y))を出し、前立てもゼッケンも
  `front_surface_sampler` で相手の頂点をそのまま線形に読む。相手のメッシュ面と
  厳密に一致するので、浮きも沈みも起きない。
  (初版は「前中心の y + 断面の楕円」で近似していたが、胸の山が左右2つになると
  前中心が谷になり、幅のある布が胸に沈んだ。近似をやめた経緯は下の節)
- **前スカートには周期成分の検査を掛けられない。** 半周ぶんの弧の半径列は円周の
  スペクトルにならず、平らな弧でも k=3 が立つ(ケープが通るのは開きが40°で弧が
  ほぼ全周だから)。`radial_modulations` を None にして外し、代わりに上端の弧長と
  広がりを**製図値**と突き合わせる。ケープも開きを大きくすると同じ誤検知に当たるはず
- **弧の分割数は奇数に丸める。** 偶数だと前中心を2頂点が跨いで、いちばん前に出る点が
  中心からずれる(ゼッケンの columns とまったく同じ罠)
- **袖ぐりの大きさは3つのパラメータの積で決まる** — 角度幅(`armhole_segments`)・
  深さ(`armhole_depth_scale`)・そして**肩線の幅**(`shoulder_width_scale`)。
  最初の版は肩線がサイズ表の肩幅(38cm)のままで、袖ぐりの上端が肩先まで開き
  「スク水にしては腕を通すところが大きい」と指摘された。水着の肩紐は肩先まで来ない。
  肩線を 0.90 に詰めると肩の渡りが 6.2cm → 4.4cm になり、肩ヨークの張り出しも消える
- **袖ぐりの深さは行数に量子化される**(`armhole_rows = round(深さ / 行間隔)`)。
  この preset では 5行=16.7cm / 6行=20.0cm / 7行=23.3cm の3択で、間の値は取れない
- **袖ぐりは丸める。** `skip_faces` は格子から矩形の面群を抜くので、放っておくと
  四隅が直角の長方形の穴になる(実物の袖ぐりは丸い)。`round_armhole` が
  **境界の頂点を楕円へ載せる** — 矩形の境界では max(|u|,|v|)=1、楕円では
  hypot(u,v)=1 なので hypot で割れば写せる。辺の中点はほぼ動かず角がいちばん動く
- **肩線を詰めると裾の高さが動く。** 肩の落差 = (肩の長半径 − 襟ぐりの長半径)×tan(肩傾斜)
  なので、肩線を詰めると側頸点が下がり、着丈の起点が動いて裾 z が変わる。
  pants と apron の `waist_z` を取り直さないと縫合が 0.7cm ずれる(seam ゲートは通るが)

### 踏んだ間違い(armhole_loops の由来)

**前を閉じた瞬間に袖ぐりの検出が壊れた。** `armhole_loops` は「境界ループのうち
**一番長い1本が外周**、残りが袖ぐり」で判定していた。前開きの胴は襟ぐり+前開き+裾が
1本につながるのでこれで正しいが、前を閉じると外周が襟ぐりと裾の2本に割れ、
**裾より短い襟ぐりが袖ぐりに化ける**。袖ぐり深さも肩の渡りも襟ぐりを相手に測るので、
数値は出るが意味が違う — 落ちずに黙って狂う種類の壊れ方だった。

対策: 「一番長い1本」ではなく「**上端リング・下端リングの頂点を含む輪を落とす**」に変えた。
前開きでも閉じでも同じ判定で、既存プリセットの結果は変わらない。

### 踏んだ間違い(袖ぐりを丸めるときの単位)

「袖ぐりが四角い」を直すのに、**まず行ごとに抜く面の幅を変えた**(上下の行を狭めて
楕円のマスクにする)。ワンピースの袖が自己交差して落ちた。

原因は**丸めの単位**。袖ぐりが3分割しかないと、中心をずらさずに取れる幅は 3 か 1 で、
1段狭めただけで境界に深さ1分割の棘ができる。袖は袖ぐりの境界ループをそのまま上端に
使って円へ寄せるので、棘がそのまま袖山に入って自分と交差した。
**下端だけ狭める・上下1段だけ狭める、どれも同じ理由で落ちた**(検証済み)。

対策は単位を変えること。面を抜くのは矩形のまま(=深さと幅の設計値はそのまま)にして、
**穴の境界頂点を楕円へ載せる**(`parts.round_armhole`)。頂点の移動は連続量なので、
角だけを必要なぶんだけ削れる。副作用は肩線リングの最外点が 0.2% 未満動くことだけで、
肩幅ゲートの許容差(3%)の内側に収まる。丸めた結果、袖の付き方はむしろ良くなった
(袖ぐりが円に近づくので袖山の寄せが素直になる)。

### ブラインド識別テストの結果(**合格していない**)

文脈ゼロの haiku に匿名パスのレンダーを読ませる工程を**16回**回した。
「スク水」には**一度も到達していない**。到達したのは「水着の仲間」まで(16回中5回)。

| 版 | 答え |
|---|---|
| 脚口 4.1cm・ゼッケンのみ | 「ノースリーブタンクトップ + 白いパネル装飾」/「ボディスーツまたはレオタード」 |
| 脚口 2.0cm | 「タンクトップ」/「紺色の無袖タイトドレス」/「胸部カットアウト付きキャミソール」 |
| + 名入れバー・前スカート | 「胸部にロゴが付いたタンクトップ」×3(**カットアウトの誤読は消えた**) |
| + 裾ビューが股を写すようになった | 「ラッシュガードまたはスイムトップ」/「ビキニ」/「スポーツブラ」/「タンクトップ」×2 |

**この工程で見つけて直した欠陥**(どれも目視では気づけなかった):

- **ゼッケンが「カットアウト(開口部)」と読まれた**(5回中3回)。文字もフチも無い
  真っ白な矩形は、布の上の布ではなく穴に見える。浮かせ量を 1.9mm → 4mm に増やしても
  変わらず、**紺の名入れバーを内側に重ねて初めて消えた**(穴の中に紺の帯は在り得ない)
- **`tools/verify.py` の "hem" ビューが裾を写していなかった。** `aim` が常に bbox の
  中心を狙うので、丈のある衣装では寄りの絵に胸が写る。**スク水の脚口は6枚のどれにも
  写っておらず**、識別器が「タンクトップ」と答え続けたのはそのため。狙う高さを
  ビューごとに指定できるようにして裾(0.12)へ向けた。これは全衣装に効く直し
- **真下から覗く仰角(-0.45)も駄目だった。** 脚口が「ブラのカップ2つ」に読まれた。
  内側の裏面ばかり写るのは backface.png の仕事なので、-0.30 に浅くした

**残っている壁(パラメータ調整では動かない。次はここから)**:

- **ゼッケンに文字が無い。** スク水を名指しさせる最大の手がかりは「名前が書かれた白い布」。
  このプラグインに**テクスチャの経路が無い**ので、今は白い矩形 + 紺の帯までしか作れない
- **素体の中に着せていない。** 中身が空の紺のシェルは、股と脚口が下からしか見えず、
  上半身が silhouette を支配する。「タンクトップ」の誤読はほぼこれ
- 高レグ(新スク)は「胴の筒に脚のラインを彫り込む」構成が要り、pants の再利用では
  作れない(脚の帯を持ち上げると胴と二重になる)。ただし**高レグにすると
  レオタード寄りに見える**ので、スク水の識別にはおそらく効かない

### 「昔のゲームっぽい」の内訳と直したもの

指摘を受けて実装を見たら、**モディファイアが1つも掛かっていなかった**
(`build.py` は素の格子をそのままオブジェクトにしていた)。CLAUDE.md の
「仕上げは標準モディファイアに投げる」が未実行の状態。切り分けた結果:

| 見え方 | 原因 | 対策 |
|---|---|---|
| 縁が紙のように薄い | 布が厚みゼロの一枚面 | **Solidify**(`fabric_thickness` 既定 0.0008/H = 1.3mm) |
| 襟ぐり・袖ぐり・裾が多角形 | 断面が24角形 | **素の分割数を上げる**(24 → 44)。Subsurf ではない |
| 全体が単色でのっぺり | テクスチャが無い | **未解決**(テクスチャ経路が無い) |

**Subsurf は却下した。** 粗い格子に掛けると制御点の内側へ縮んでウエストの締まりが
消え、全体が膨れて風船に見えた。ゼッケンも厚い板になった。滑らかさは素の分割数で
出すのが正しい。つまみ(`subdivision`)は残したが**既定は 0**。

Solidify の設定で踏んだ罠(どれも層2の評価後メッシュ検査が捕まえた):

- **厚みは内向き(`offset: -1`)。** 外向きにすると胴の表面が浮かせ量を追い越して、
  ゼッケンが布に沈んだ。ゼッケンも前垂れも「相手の**外側の面**から standoff だけ
  浮かせる」で組んであるので、外側の面が動いてはいけない
- **`use_even_offset` は切る。** 鋭い折れ目で 1/cos に比例して伸び、股の縫い目に
  棘を作る(自己交差 26 件)
- **`solidify_mode` は NON_MANIFOLD。** 股の分岐のように面が鋭く折り重なる所は
  単純押し出しではシェルが交差する(26 → 4 件)

### 胸がとがりすぎ — **バスト周を二重に数えていた**

嘴を直しても横から見ると円錐のようにとがっていた。前面の稜線を測ると
頂点へ向かう傾き dy/dz が **+1.25(51度)**まで立ち、通り過ぎると −0.22 に落ちる。
上りが急で頂点の折り返しが鋭い形。

`bust_axial_width` を広げても効かなかった(51.3度 → 50.2度)。上側は襟ぐりで
頭打ちなので、広げても効かないのが道理。効くのは**ふくらみの量**だった。

そして量が過大なのには理由があった: **断面の楕円はバスト周(83cm)から作っている
ので、胸のふくらみはもう楕円に入っている。** その上に実物の胸の高さ(4-5cm)を
足すと二重計上になる。ここは「楕円だけだと平ら」を崩す程度の量でよい。

スク水は `bust_projection` 0.020 → **0.012**(1.9cm)。

**追記(PR #10 レビュー): 上の「既定 0.022 も立ちすぎ」は誤りだった。**
根拠にした 58度/71度は下のゲートの初版で測った値で、実際には胸ではなく
**肩ヨークの傾き**を測っていた(次節)。指標を直して測り直すと、既定 0.022 の
ブラウス/ベストは 24.8度で問題ない。

**同じ量でも丈の短い胴では立つ。** ワンピースは胴の span が 0.313m しかなく
(ブラウスは 0.546m)、同じ 3.5cm のふくらみが 7.7cm の落差に押し込まれるので
稜線が 57度になる。ここは**あえて直していない** — 既存の見た目を変えるうえ、
警告としては「量を減らせば通る」ことが確かめられている(0.010 で 36度)ので、
届かない warn ではないため。

### 稜線の角度をゲートにした(`bust_is_not_a_cone`)

胸まわりは**同じ場所を3回直した**(単一ドーム → 襟ぐり突き抜け → 量の二重計上)。
3回とも正面のレンダーでは分からず、横から見る/数値で測る、で初めて出た。
`bust_projection` は「ふくらみが**在るか**」を下限で見ていたが、
**在りすぎて円錐になっていないか**は誰も見ていなかった。

`validate.bust_ridge_degrees` を足した。高さで区切って各区間の最前点を拾い、
**頂点より上**の最大傾きを度で返す(下は腰へ向かう自然な falloff なので見ない)。
しきい値 45 度で **warn**(公表寸法のある値ではなく形の質の指標。hard にすると
既存プリセットが落ちる)。

測るときに踏んだ罠が3つ。**3つめが本命で、初版は名前どおりのものを測っていなかった。**

- **襟ぐりより上を外さないと稜線を取り違える。** 肩紐や襟ぐりの縁の段差を
  胸の稜線と読んで、スク水の 37 度が 55 度に化けた。`z_max` で切る
- **区間の代表点は「その頂点の実際の z」で持つ。** 区間の中央を使うと外側の
  包絡線をなぞる形になり、角度が約6度ぶん過大に出た(三角形の合成データで
  理論値 45 度に対し 51.6 度)。ただし実際の z を使うと、襟ぐりの前下がりで
  代表点どうしがほぼ同じ高さに来て傾きが跳ねるので、**高さの差が区間の半分に
  満たないペアは飛ばす**。この形なら合成データで理論値と厳密に一致する
- **上へ広く取ると胸ではなく肩ヨークを測る**(PR #10 レビューで発覚)。
  初版は「頂点より上の**最大**傾き」を見ていたが、その最急区間は胸ではなく
  **胸から襟ぐりへ布が引けていく肩ヨークの区間**だった。証拠は単純で、
  `bust_projection` を 0 にしても 54.8 度が残る。0.018 以下は全部この床に
  張り付いて指標が動かない = **しきい値 45 度に胸のパラメータでは到達できない**。
  直せない warn はいずれ無視されるので、ゲートとして有害だった。
  **頂点の近くだけ**を測るように変えると床は 6.1 度まで落ち、量に単調に反応する
  (0.0→6.1 / 0.012→16.6 / 0.022→24.8 / 0.040→37.1 / 0.080→54.7 度)
- **窓の広さを「隣の代表点まで」にすると分割数で読みが変わる**(同レビュー B)。
  同じワンピースが rings 12/36/72 で 26/58/62 度になった。粗いほど窓が広く、
  傾きが均されて**実際より緩く出る** — つまり低ポリほど甘く判定していた。
  窓を**走査範囲に対する比**(`BUST_RIDGE_WINDOW`)で取ると分割数に依らず
  1 度以内で一致する。走査範囲の上端(`bust_top_z`)は、上側が襟ぐりで
  詰められている胴では**襟ぐりの z と代数的に一致する**ので範囲としては
  ほとんど効かない。床を消したのは窓のほう

同梱プリセットの実測(修正後): スク水 27.0 / ブラウス・ベスト 24.8 /
ワンピース 57 度。ワンピースだけ warn だが、**量を 0.010 にすれば 36 度で通る**
ことを確認済み(= 直せる warn)。

### 胸のふくらみが襟ぐりを突き抜けていた(全衣装に共通・**横から見ると嘴**)

正面は直っても横から見ると胸の前に鋭い角が出ていた。測ったら
**ふくらみの上端が前中心の襟ぐりより上にあった** — 同梱の胴プリセット4つとも
19〜29mm はみ出していて、襟ぐりの縁そのものが前へ押し出されていた。
布が無いところまでふくらませていたので、縁が嘴になるのは当然だった。

対策: `bust_projection` に `axial_width_up`(上側だけの半幅)を足し、
builder が**襟ぐりまでの余裕**から詰める。下側は spec の指定のまま
(実物の胸は下へ長い)。頂点では上下とも値 1・傾き 0 なので、幅が違っても
折れ目にはならない。詰めた値は design に出して、設計値と実物がずれないようにする。

頂点の高さも直した: スク水は `bust_t` 0.34 → 0.44(頂点 z/H 0.747 → 0.725。
実物のバスト位置は約 0.72H)。**測定値は行に量子化される**ので、
bust_t を 0.40〜0.46 で振っても同じ行に落ちる。

### 胸のふくらみが**前中心で1つの山**になっていた(全衣装に共通)

`modulate.bust_projection` は前中心を頂点にした余弦の山を1つ作っていた。
つまりいちばん前へ出るのが胸骨の位置で、実物では逆に窪むところ。
胸に1枚のドームが乗ったように見えていた。

対策: `bust_apex_degrees`(既定 22度、**設計値**)を足して**左右2つの山**にした。
各山の半幅は `angular_width - apex` に取るので、**総半幅は apex を動かしても
`bust_angular_degrees` のまま**(袖ぐりに掛かる範囲が変わらない)。
山の重ね方は和ではなく max — 足すと前中心で山を超えて逆に盛り上がる。

**この変更で前立てとゼッケンが胸に沈んだ**(交差 18 件 / ブラウス 10 件)。
どちらも「前中心の y + 断面の楕円」で貼り位置を近似していたので、前中心が谷に
なった瞬間に、幅のある布の端(胸の山の上)が布の中へ入った。
対策は近似をやめること — 胴が前面の**実物**(`front_surface`: 行ごとの (x, y))を
出し、前立てもゼッケンも `front_surface_sampler` でそこを読む。相手の頂点を
そのまま線形に読むので、相手のメッシュ面と厳密に一致する
(「依存パーツは相手の実物から作る」の原則どおり)。

### 継ぎ目が「布の切れ目」に見える(全衣装に共通)

ウエストに1本の線が見えた。切り分け:

| 調べたこと | 結果 |
|---|---|
| 寸法の段差か | **違う**。胴の裾とブリーフの上端は 5μm で一致 |
| 面の傾きの折れか | **主因ではない**。継ぎ目の折れは 8.0°。リング密度を上げて 5.9° に半減させても線は変わらなかった |
| 別オブジェクトだからか | **これ**。Blender は別オブジェクトの頂点法線を繋がないので、面が連続していても陰影が割れる |

**スク水だけの問題ではない** — ワンピース(胴+スカート)、スカート(バンド+本体)、
パンツ(バンド+本体)も同じ構造なので同じ線が出る。

対策は `join_seams`(**既定 False**)。True にすると `parts.seam_groups` が joints で
繋がったパーツをまとめ、`build.py` が結合 → 継ぎ目の頂点を溶接 → そのあと厚みを付ける。
**順序が重要**で、先に Solidify を積むと継ぎ目の両側にリム(境界を塞ぐ帯)ができてから
溶接することになり、内側に板が残る。

既定を False にしたのは、統合すると出力オブジェクトが減ってパーツ単位の編集
(リギング・マテリアル差し替え)ができなくなるため。層2は
「1パーツ = 1オブジェクト」前提の検査(頂点の一致・折り目の本数)だけを外す。
**評価後メッシュの検査は外さない** — 溶接に失敗すれば非多様体や重複頂点として
そこで落ちる。

**外すのは実際に統合された組だけ**(`len(group) > 1`)。初版は `join_seams` を
全体フラグとして使っていたので、統合されていない単独パーツ(ゼッケン・前垂れ)の
hard ゲートまで黙って消えていた(スク水で 10 件 → 0 件。PR #10 レビュー)。
コメントには「黙って緩めない」と書いてあったのに、実際は緩んでいた。

### 踏んだ間違い(分岐→円の移行が1行で終わる)

残った4件の自己交差は**厚みをいくら薄くしても消えなかった**(0.16mm でも同じ件数)。
座標を出したら脚口の 17mm 上、左右の脚の外側。原因は `leg_rings: 3` × `blend: 0.3` で
**blend の区間にリングが1本も入らず、分岐リング→円の移行が1行で完了していた**こと。
折り返しに近い折れ目なので、厚みを付けた瞬間にシェルが交差する。

**層1では捕まらない**(面同士は交差していない)ので `build_pants` に下限を入れた:
`leg_rings × blend >= 1.5`(実測: 1.2 で落ち、1.5 で通る。股下の長さには依存しない)。
PR #8 の「粗い割りでも thigh ゲートが消えない」テストは、下限を満たす粗さ
(leg_rings 6 / 8)で同じ意図を検査するよう書き換えた。

### 残っている warn(理由つき)

- `Swimsuit_Brief.edge_length_cv_axial` = 0.53(しきい値 0.40)。腰〜股(24cm)と
  脚口の帯(2cm)が**1つのパーツに同居する**ので軸方向の刻みが揃わない。
  水着のプロポーションでは避けられないので、丈のほうを優先して warn を残した
- `edge_length_over_h` = 0.0128(実測レンジ 0.0206-0.0311)。**意図的にレンジより
  細かい。** このレンジは VRM アバター(ゲーム用アセット)の実測なので、
  多角形に見えない滑らかさを出すには割り込む必要がある。素の格子を粗いまま
  Subsurf で誤魔化すより、素の分割数で出すほうが形が崩れない

## フード (hood)

首の縫い目から頭を包み、先端へ絞る前の開いたシート。襟(collar)との違いは
**頭が入る大きさと高さがあること**、帽子との違いは**首に縫い付いていること**。

### 参照した寸法

| 項目 | 値 | 出どころ |
|---|---|---|
| 頭囲 | 0.35 /H(158cmで約55cm) | 公表値(AIST 人体寸法データベースの成人女性 約55cm)を丸めた**設計値**。実測はしていない |
| 全頭高 | 0.14 /H(約22cm) | 同上 |
| ゆとり・高さ倍率・開口角 | spec 指定 | **設計値** |

### 定義(この4つが揃って初めてフードになる)

| # | 定義 | 生成側 | 検証側(**先に決める**) |
|---|---|---|---|
| 1 | **首の縫い目に付いている** | リング0 = host(cape / bodice)の top リングの頂点そのもの | shared joint の対応頂点ずれ ≈ 0 |
| 2 | **頭が入る太さ** | 最大リングの半径 = 頭囲×(1+ゆとり)/2π | 一番太いリングの弧長 ≥ 頭囲×(1+ゆとり)×3/4(`hood_wraps_the_head`) |
| 3 | **頭が入る高さ** | 高さ = 全頭高 × height_scale | 縫い目の上端から頂までの実測 = 設計値 ±5%(`hood_depth`) |
| 4 | **顔の開口が開いている**(かぶると顔が出る) | 前開き角を host の楔から face_open_degrees へ広げる | 開口の弦長 ≥ 設計弦長の半分(`hood_face_open`) |

### 実装メモ

- builder は `parts.build_hood`(DEPENDENT。host の top リングが必要)
- **キャップは張らない。** `all_quads` がハードゲートなので三角ファンで頭頂を
  閉じられない。buttons と同じく先端を小さな弧(tip_ratio)まで絞って終える
  (尖ったフードとして読める)。境界ループは外周1本
- 頂点数はリング間で変えられないので、顔の開口は**角度の再配置**で広げる
  (前中心まわりの相対角を、縫い目の配置から目標の開口角の等分へ blend)
- リングは下(縫い目)から上へ計算して**逆順で loft に渡す**(巻き方向の規約は
  「上から下へ積む」。順で渡すと全面が裏返る)
- 中心が後ろへ逃げるので `tubular=False`(radial 判定と周期成分検査は掛けない。袖と同じ)

## ケープ (cape / capelet)

首まわりから肩の上を通って裾へ広がる、前の開いた1枚のシート。袖が無いのが
トップスとの違い、肩に「乗る」(ウエストに乗るスカートと違い吊り点が首)なのが
スカートとの違い。

### 参照した寸法

| 項目 | 値 | 出どころ |
|---|---|---|
| 首回り | 36cm (/H 0.228) | 文化式(サイズ表の `neck` を流用)|
| 首回りのゆとり | +35% | **設計値**。肩の上に布が乗るぶん襟ぐり(+12%)より大きい |
| 丈・広がり・前開き角 | spec 指定 | **設計値**(製品実寸は未参照)|

### 定義(この4つが揃って初めてケープになる)

| # | 定義 | 生成側 | 検証側(**先に決める**) |
|---|---|---|---|
| 1 | **首まわりから掛かる。** 上端が首の寸法に合う | 上端の弧長 = 首回り×(1+ゆとり)から前開きの楔を除いた楕円弧(数値積分) | 上端境界の実弧長が製図値 ±3%(`cape_top_arc`) |
| 2 | **前が開いている**(かぶりものではない) | 前中心に楔状の開き(`front_open_degrees`) | 境界ループが1本 かつ 裾の開き幅が設計値 ±10%(`cape_front_open`) |
| 3 | **肩から裾へ広がる**(広がらなければただの開いた筒) | flare を弧長比で掛ける | 裾弧長/上端弧長 ≥ 1.3(定義の下限)かつ設計比 ±3% |
| 4 | **丈が肩線より下** | length /H | 上端z−下端z = 丈 ±3%(既存 length ゲート)|
| 5 | **肩がある**(ただの円錐はスカートに見える) | 首→肩線(首の下 0.045H)で幅を肩幅×1.1 まで一気に広げ、以降を flare で裾へ(ハンガー型) | 肩線近傍のリング行の x 差し渡し = 肩幅×1.1 ±3%(`cape_sits_on_the_shoulders`) |

### 実装メモ

- builder は `parts.build_cape`。bodice を使わない — bodice は design に
  `shoulder_width` を入れるのでブラウス固有ゲート(シャツテール・胸のふくらみ・
  製品着丈)が発火する。ケープはケープのキーだけ申告する
- 楕円は弧長が角度に比例しない(前面の弧が濃い)。「周長×角度割合」の近似は
  開き40°で 2.3% ずれて DIM_TOL(3%)を食い潰すので、製図値は `modulate.ellipse_arc`
  (数値積分)で出す
- 首の縁の始末は `collar` を `attach_to` で乗せる(cape の top リングは collar の
  host としてそのまま使える)。リングは水平のまま(前下がりは未実装)

### 踏んだ間違い(定義 #5 の由来) — ブラインド識別テスト

**文脈を知らない視覚モデル(haiku)にレンダー3枚(斜め・正面・横)だけを見せて
「何に見えるか」を答えさせたところ、ケープは「ラップスカート」、フード付きは
「ベル(鈴)」と誤読された。** 数値ゲートは全部通っていた — 原因3(組み上がりの
見た目を誰も見ていない)の変種で、「作った本人は文脈を知っているので見た目の
曖昧さに気づけない」。ただの円錐にはスカートと区別する形状特徴が無かった。

対策: 肩の張り(定義 #5、ハンガー型プロファイル)を入れたところ、同じテストで
「ケープ(マント)」「フード付きクローク」と正しく識別された。パンツも同様に
「マネキンの下半身」と誤読され、ゆとり増(ease 0.08 / thigh_ease 0.15)+
ストレート脚(knee_scale 1.15)+布らしい色で「パンツ」と識別されるようになった。

**この「文脈ゼロのブラインド識別」は新しい衣装を足したときの検証工程として使える**:
レンダーを匿名パスに置き(パスに衣装名を入れると視覚モデルがそこから答えを
当ててしまう)、「同一物体の3アングル」とだけ伝えて識別させる。

### 前の版で踏んだ間違い

胴を**ただの筒**にしたため、上端リングが「襟ぐり」と「肩線」を兼ねてしまい、
肩の面が作れず上が漏斗状になった。数値ゲートは全部 PASS した — 上の #1〜#6 が
どれも検証項目になっていなかったから。**定義を書く前にコードを書いたのが原因。**

### この版の作り(K1 のまま解けた)

首の穴と肩線を**別々のリング**にすれば、その間の帯がそのまま肩ヨークになる。
新しいカーネルは要らず、リングの並べ方だけの問題だった:

```
リング0: 襟ぐり(小さい・肩より少し高い)   ← 上端の境界 = 襟ぐり
リング1: 肩線(肩幅)                        ← 0→1 の帯が肩
リング2..: バスト → 裾                      ← 1→2 以降に袖ぐりの穴を開ける
```

**袖山が曲線でない**という限界は残る。まっすぐな筒なので袖山の縫い目長と筒の周長が
一致しない。筒の太さは `bicep_scale`(設計値)で決め、縫い目長は別に報告する。

### この版の到達点と残っている問題

定義 #1〜#5 は検証項目になり、実測で通っている(身長158の設計値に対して):

| 定義 | 設計値 | 実測 |
|---|---|---|
| #3 肩幅 | 0.3697 m | **0.3674**(誤差 -0.6%) |
| #2 襟ぐり周長 | 0.4277 m | **0.4268**(-0.2%) |
| #4 袖ぐり深さ | 0.2070 m | **0.1936**(-6.5%、許容15%) |
| #1 肩の渡り幅 | 0.1114 m | **0.1072**(-3.8%) |
| #5 袖ぐりの位置 | 体側 | x=±0.166 / y=0.000 → 体側 |

**袖の直し(済)**

袖の上端リングを**袖ぐりの境界ループそのもの**にした。穴の頂点をそのまま使うので
継ぎ目は定義上ゼロ(実測 3.03e-17)、そこから `cap_fraction` ぶんのリングをかけて
「穴の形 → 円」へ寄せる過程がそのまま袖山になる。
そのため**袖の周方向分割数は spec で指定しない**(袖ぐりの境界頂点数で決まる)。

定義 #6 も検証項目にした: 肩先から袖の下端までの距離 = 袖丈 ±8%
(実測 0.5438 / 設計 0.5293 m)。

| 定義 | 設計 | 実測 |
|---|---|---|
| #6 袖丈(肩先→袖下端) | 0.5293 m | **0.5438**(+2.7%) |
| 袖ぐりと袖山の継ぎ目 | 0 | **3.03e-17** |

**周期成分の検査は Z軸まわりの筒にしか当ててはいけない。** 傾いた袖のリングを
XY平面で測ると円が楕円に見え、存在しない周期成分(k=6・振幅0.118)を検出して落ちた。
`mesh.tubular` で場合分けするようにした。

## ブラウスが「ブラウスに見えなかった」理由 — 工程の反省

定義 #1〜#6 が全部 PASS した状態でレンダーを見たら、**煙突つきの寸胴に針のような
円錐が水平に刺さったもの**だった。数値は全部合っているのに、誰も服だとは言わない。
原因は工程にある。

### 原因1: すべての定義が「点と点の距離」で、**形**を1つも測っていなかった

#1〜#6 は肩幅・襟ぐり周長・袖ぐり深さ・肩の渡り幅・袖丈 — 全部**ランドマーク間の距離**。
距離が合っていても、その間をどう繋ぐかは無制限に自由なので、吹き流しでも合格する。
これは character-modeling スキルの `form.md` §0 が記録している失敗と同じ形
(ウェイト・トポロジ・対称性・ポリゴン予算が全部合格したまま腕が円柱・尻が無い)。

**対策: 定義に「形」の項目を足す。** 断面の推移・軸の向き・輪郭の折れ — 「距離」ではなく
「プロファイル」を測る項目を持つ(#10 #11 が該当)。

### 原因2: **無い機能は、ある物を測っても検出できない**

前立てもボタンもカフスも襟の折り返しも無かった。どんな計測をしても「無い」ことは
落ちない。**「ブラウスに見える」の正体の大半は、寸法ではなくこれらの部品**である。

**対策: 定義に「その部品が存在すること」を書き、個数・寸法・位置を検証する**(#12〜#14)。
存在しないパーツはゲートが `KeyError` ではなく **FAIL** になるように、
設計値(`design`)側に必ず期待値を置く。

### 原因3: パーツ単位でしか見ておらず、**組み上がりの見た目を誰も見ていなかった**

胴も袖も襟も個別には合格していた。合わさった姿を判定する工程が無かった。
レンダーは出していたが、**合否には効かない参考画像**でしかなかった。

**対策: 「毎回レンダーを見る」を工程に固定する。** 数値ゲートは回帰のための網であって、
「これは服か」の判定ではない。判定は目でやる。ただし目で見つけた欠陥は
**必ず数値ゲートに翻訳してから直す**(でないと次に壊したときに気づけない)。

### 原因4: 参照した寸法が「人体」ばかりで、**製品の実寸**を見ていなかった

JIS・文化式から取ったのは人体寸法。**服の寸法ではない。**
着丈は人体寸法表には存在しないので、決めないまま `hem_z` を勘で置いていた。
結果は実寸の6割の丈 = クロップ。「未定義の値を勘で置いた」ことが、
「丈・肩幅・袖丈の相互の比を定義していない」の正体だった。

**対策: 製品の実寸表を一次情報として持つ**(下表)。

| # | 定義 | 生成側 | 検証側 |

**#15 を後から足したのは、#14 が「個数・間隔・位置」しか測っていなかったから。**
これは #1〜#6 で踏んだ「距離しか測っておらず形を測っていない」とまったく同じ穴で、
**部品を足したこと自体に満足して、その部品の形を定義し忘れた**。
パーツを1つ足すたびに「そのパーツの形の定義」も要る。

### 参照した実物(シャツ用の貝ボタン)

| 項目 | 実物 | 出どころ |
|---|---|---|
| 直径 | **11.5mm**(前身頃)。9 / 10 / 11.5 / 13mm がよく使われ、袖口は 9〜10mm | 貝ボタン販売(高瀬貝 11.5mm)・ボタンの解説 |
| 厚み | **2.3mm**(1.5〜5mm の幅がある) | 同上(高瀬貝 11.5mm 厚2.3mm 4穴) |
| 穴 | **4つ**。中心寄りに集まっている | 同上 |

厚み/直径 = 2.3/11.5 = **0.20**。前の版は迫り出し 2.9mm / 直径 11.1mm = 0.26 の
**円錐**で、裏面が無く穴も無かった。数値としては直径だけ合っていて、
形は真珠のスタッドに近かった。

**穴は「窪み」ではなく本当に開ける。** 最初は皿のリングの頂点を4つ奥へ押した
窪みにしたが、寄って見ると陰影がぼやけて穴に見えなかった。面を抜いて開けると
(袖ぐりと同じ `skip_faces`)、検証側も **穴 = 4頂点の境界ループ**として数えられる。
窪みだと「押した頂点の数」= 生成側の申告に近い量を数えることになっていた。

**硬い部品にはスムーズシェーディングを掛けない。** 円盤の縁が丸まって、
寄ると白い塊にしか見えない。`PartMesh.flat_shaded` を足して布と分けた。

**エッジ長 /H の指標から硬い部品を外した。** 参照レンジ 0.0206-0.0311 は
Bottoms の**布メッシュ**の実測でボタンを含まない。直径11.5mmの部品を混ぜると
平均を押し下げ(0.0199 → 0.0143)、「布の粗さ」という指標の意味が消える。
分けたら布は 0.0230 でレンジ内に戻り、ボタンは 0.0009 として別に報告する。

**#10 のような「宣言値との一致」を検証項目に入れてよいのは、値の根拠を
別に明記したときだけ。** そうでないと「コードが指示どおり動いたこと」しか確かめておらず、
サブエージェントのレビューが指摘した「恒真のゲート」になる。

### ゲートを書くときに踏んだ罠(3つとも同じ形)

**どれも「ゲートが自分で無効になる」形の罠。** 実装が壊れているのではなく、
検証が逃げる。テストは「正しい入力で通る」だけでは足りず、
**壊した入力で落ちること**まで見ないと気づけない。

| 罠 | 起きたこと | 直し方 |
|---|---|---|
| **判定区間を spec のパラメータで決めた** | 「肘まで袖幅を保つ」を `elbow_fraction` までで判定した。テーパーを早く始めると判定区間も一緒に縮んで、円錐が通った | 肘は**解剖の位置**(袖丈の半分 `SLEEVE_ELBOW_T`)で固定する。spec を動かしてもゲートは動かない |
| **設計値が 0 のときゲートごと消えた** | `if design.get("front_neck_drop")` にしていたので、前下がりを 0 にすると判定が消え、水平な襟ぐりが通った | 突き合わせ相手を**製図の値**にし、条件を `in design` にする。胴には必ず襟ぐりがあるので常に判定する |
| **「幅が設計どおり」だけ見て、覆えているかを見なかった** | 前立て幅 3.0cm は設計どおりだが、前開きの隙間が 3.3cm あって覆えず、裾のアップで黒い筋が出た | `placket_covers_the_opening` を別に足す。**相手との関係**を測る項目が必要 |
| **実測のつもりで生成側の申告を測っていた** | ボタンの間隔・z位置を `design["button_zs"]` から計算していた。メッシュの頂点を間隔の45%動かしても間隔CV 5.7e-16 で合格した(PR #7 のレビューで実証された) | 境界ループの重心からボタンの高さを復元する。**メッシュだけから出せる量に限る** |

**5つ目は、この表を書いたあとに自分でもう一度作った。** ボタンの穴は
「押した頂点の数」から「境界ループ」へ直したのに、同じ関数の中の**間隔と z 位置は
申告のまま**にしていた。罠を言語化しても、次に書くコードで自動的に避けられるわけではない。

**対策として回帰テストの形を決めた: 「メッシュを壊してゲートが落ちること」を直接テストする。**
入力(spec)を壊すテストでは、生成側と検証側が同じ申告を見ている限り両方が一緒に動くので
穴が残る。`test_moving_a_button_in_the_mesh_breaks_the_spacing_gate` は
**頂点だけを動かして design はそのまま**にする。これなら申告を測っているゲートは必ず落ちる。

**では逃げてよいゲートは無いのか。** ある。基準は「**その値を外した物も、その衣装か**」。

- `neck_drop_scale = 0`(前下がり無し)→ **無い。** 前下がりの無いブラウスは存在しない。
  だからゲートは製図の値と突き合わせ、spec では逃げられないようにした
- `length_scale = 0.6`(着丈6割)→ **ある。** クロップ丈のブラウスは実在する服なので、
  丈は正当な設計の自由度。ここは spec に従わせてよい

**ただし「逃げられる」と分かっているゲートは、逃げていないことを別に押さえる。**
着丈は `length_scale` と一緒に設計値も縮むのでパーツ単位のゲートは通る。
プリセットが実寸から外れていないことは
`test_garment_length_matches_the_product_measurement`(着丈 65cm ±8% を直接固定)が見る。
**パーツのゲートは「spec どおりに作れたか」、プリセットのテストは「その spec が実寸か」**
という二段構えで、どちらか片方だけでは足りない。

3つ目に付随して2つ直した。**前開きの隙間を分割数の副産物にするのをやめた**
(28分割で 3.3cm。分割数を変えるだけで前立てからはみ出す)。それと
**前立ての縦の刻みを胴の前面プロファイルと同じ z にした** — 等間隔に刻むと、
襟ぐり→肩線で前面が 4.5cm の間に 5cm 前へ出る区間を前立てが直線で跨いで
胴の中へ食い込み、`part_intersections` に落ちた。袖の周方向分割数を袖ぐりから
決めたのと同じで、**相手の実物に合わせる**のが正しい。

同じ「相手の実物から作る」に揃えたので、依存パーツは袖だけでなく
襟・襟の羽根・前立て・ボタンにも広がった(`DEPENDENT_TYPES`)。ボタンは前立てに、
前立ては胴に付くので依存が二段になり、`build_all` は真の依存順で組む。

## ブラウスの定義(続き2) — 寄って見て分かった3つ

全体像がブラウスになったあと、**寄って**見たら3つ残っていた。
遠景では気づけないので、正面・斜め・背面だけでなく**部位のアップ**も見る。

| # | 定義 | 生成側 | 検証側 |
|---|---|---|---|
| 16 | **裾がシャツテール**(水平に切られていない)。脇がいちばん高く、前後の中心が下がる | 裾のリングの z を角度で変える(`shirttail_drop`。襟ぐりの前下がりと同じ形) | 脇の裾 z − 前後の裾 z が設計どおり ±25%、かつ前後とも脇より下がっている |
| 17 | **カフスが見える。**袖口の手前が絞られて帯に段差ができる | `cuff_gather`(いせ込み)で袖口直前を太くし、付け根のリングをシャープに | 直前のリング周長 / カフスの周長 ≥ 1.10 |
| 18 | **胸のふくらみがある**(これが無いとメンズシャツ) | 前中心・バスト高さに局所的な出っぱり(`bust_projection`) | いちばん前に出た点が裾の前面より ≥1.5cm 前、かつその高さが丈の上半分 |

**#17 は「幾何としては在るのに絵では見えない」の実例。** カフスの帯は
`cuff_band_is_flat` で「一定である」ことが測れていたが、silhouette に段差が
無かったので、寄ると**ただの筒を切った端**だった。これは原因3(組み上がりの姿を
誰も見ていない)のミニチュアで、**「在るか」ではなく「見えるか」を測る量**が要る。

**#16 と #18 の数値は設計値。** 製品実寸表にも製図資料にも「裾のカーブの深さ」
「胸が前へ何cm出るか」は無かった。**測っていないものを実測として書かない**。

裾がカーブすると実周長が上下動のぶん伸びて DIM_TOL 3% を超えるので、
`ring_metrics` に `perimeter_xy`(水平投影)を足し、胴の裾だけそちらで比べる。
襟ぐりの周長で同じ問題を解いたときと同じ手。水平なリングでは両者が一致するので
スカートには影響しない(テストで固定した)。

### ここから先は別の種類の仕事

決定的なメッシュ生成で届くのはここまで。残っている差は
**布のふるまい**(自重のしわ・たるみ)と**表面のディテール**(ステッチ・織り)で、
前者は Cloth シミュレーション、後者はテクスチャ/ノーマルマップの領域。
Cloth は非決定的でテストが書けないので計画段階で主軸から外してある
(`docs` 冒頭の方針と同じ理由)。**やるとしたら別の工程**になる。

**手を付けないと決めたもの:**

- **袖ぐりの継ぎ目が折り目のように立つ** — これは縫い目であって、実物の
  セットインスリーブにも縫い目はある。滑らかにするには「袖の上端リング =
  袖ぐりの境界ループ」という不変条件を捨てることになり、継ぎ目 1e-17 を失う
- **前立ての左右の重なり** — 通常の視距離では見えない

### 残っている warn(理由つき)

- `edge_length_over_h` 0.0199(参照レンジ 0.0206-0.0311)。ボタン(直径1.1cm)の
  小さい面が平均を引き下げている。参照レンジは Bottoms の実測なのでボタンを含まない
- `Blouse_Buttons.edge_length_cv_ring` 0.60。ドームは外周→中心へ半径が変わるので
  周方向のエッジ長がばらつくのは構造上正当
